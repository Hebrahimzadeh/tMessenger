Security:
- **Ownership is re-checked server-side at every attachment step**, never trusted from a prior one: `recordUpload` and `finalizeAttachment` both re-load the attachment and compare `ownerId` to the session user (`NotAttachmentOwnerError` → 403); `createCard`/`updateCard` accept an attachment id only if it is the caller's, `READY`, and not already on another card — enforced *twice*, once in the service and once by the transaction's filtered `updateMany` + count check, so a race can't smuggle one in.
- **Content type is only ever what the bytes say**, not what the client declares — the upload route has no client-supplied content-type field at all; `sniffContentType` is the sole source, and a `null` (unrecognized) result is an outright rejection. A file whose real type isn't on its declared kind's allowlist is `REJECTED` at finalize and its stored object is deleted.
- **A non-`READY` or `REJECTED` attachment can never leak**: it is filtered out before rendering and before any `getSignedRead`; there is no route that returns an attachment by id, only the card view, which applies that filter. `getSignedRead` is still the only read path object storage exposes (Task 03).
- **Card views are public only for a `PUBLISHED` space** — `getCard`/`listCards` return 404 for a draft/suspended/archived space's cards, and a caller cannot distinguish "no such card" from "space not public".
- **The upload body limit is enforced per-route** (`bodyLimit: 25 MiB + 4 KiB`) so a large-body DoS is rejected by Fastify before the handler; `recordUpload` re-checks the size and `finalizeAttachment` checks it a third time against the stored `sizeBytes`.
- Link and location inputs are stored verbatim with **no server-side URL fetch** — no SSRF surface is introduced.

Reviewer note:
- **The upload is server-proxied on purpose.** The existing `StorageProvider` (Task 03) exposes only `putPrivate(body)` / `getSignedRead` / `delete` — there is no presigned-PUT capability, and adding one would be a real new S3-surface decision outside this task's scope. So the client sends raw bytes to `POST /v1/storage/uploads/:attachmentId` and the API writes them. This keeps every byte passing through one place that sniffs, sizes and checksums before storage — which is exactly where the plan wants those checks — at the cost of the API proxying upload bandwidth. A later task can add presigned PUT behind the same intent/finalize contract without changing the client flow.
- **`Card.kind` and `CardSemanticProfile.inferredKind` are deliberately separate.** `kind` is the author's own, always-correctable label (defaulting `AWARENESS` so nobody is forced to classify); `inferredKind` is a throwaway rule-based guess kept alongside it, recomputed on every edit, that Task 25 will swap for a real model behind the same shape. Nothing in this task ever lets the inference overwrite the author's `kind`.
- **`updateCard` appends attachments; it never removes them.** "no physical deletion" makes attachment *removal* on edit an open question (soft-flag? new revision's attachment set?) that the plan doesn't settle. Rather than guess, an edit can only *add* — documented in the service. A later task that introduces a real "remove attachment" affordance can decide the model then.
- **`listCards` ordering is pure recency for now.** The plan says "ترکیب تازگی/relevance ... reaction بعداً فقط وزن ضعیف می‌گیرد" — reactions don't exist until Task 15, so there is no relevance term to mix in yet. The keyset is `(publishedAt, id)`, which a weak relevance score can extend later without breaking the cursor contract.
- **`packages/space-health` was touched narrowly and on purpose.** Task 13 shipped `cardCount` as an explicit `0` stub with a comment saying "Task 14+". Task 14 adds the Card model, so leaving the stub would have been a knowing lie in a health signal owners read. The change is one `prisma.card.count` + folding the latest card into `lastActivityAt`, with a matching real-Postgres test; no other space-health behavior moved.
- **The 25 MiB attachment ceiling is a single deliberate default**, not a plan-specified value — one ceiling for every uploadable kind, easy to split per-kind later via `ALLOWLIST`-adjacent config without touching the state machine.

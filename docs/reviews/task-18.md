Security:
- **A view can only ever be attributed to a real, session-verified user** - `POST /cards/:id/views` requires a session (401 otherwise); there is no anonymous-view code path anywhere, so "bot/internal traffic" (which never authenticates) is excluded structurally, not by a heuristic that could be fooled.
- **The admin metrics route is SUPERADMIN + MFA-gated exactly like every other admin route** - reusing `requireRole('SUPERADMIN')` rather than a new, separately-reviewable authorization primitive that could drift from the existing one.

Reviewer note:
- **A real E2E flake was found and fixed via the actual test run, not assumed**: the freshly-added `awareness.spec.ts` and a re-run of the full spec set initially failed almost everywhere with "route not found" / navigation timeouts. The cause was mundane but real - `PORT=4301 npx tsx services/api/src/server.ts` had been started *before* this task's route/schema changes and was never restarted (`tsx` does not hot-reload), so the running process genuinely lacked the new routes. Restarting it fixed every failure at once; this is a testing-workflow lesson, not a product bug, and is recorded here because it is exactly the kind of "looked like everything broke" failure worth a clear paper trail.
- **`--workers=2` was needed for one full-spec-set run this session, `--workers=1` was not** - running all of `baseline`/`auth`/`profile`/`spaces`/`ladder-flow`/`awareness` at Playwright's own default parallelism (this machine's CPU count) produced OTP/navigation timeouts that a lower worker count did not; each spec still logs in with its own fresh, randomly-generated phone number (no rate-limit collision), so this reads as local resource contention (a dev-mode Next server, Postgres, Redis, and the API all sharing one machine under N-way parallel browser automation) rather than any change in this task's own reservation/session code. Flagging the workaround explicitly rather than silently baking `--workers=2` into a config change this task doesn't otherwise need.
- **"retention شناسهٔ خام analytics را حداقل کن" is read as scoped to the analytics/dashboard layer specifically, not the raw event log itself.** `AwarenessEvent` (the per-user participation log) necessarily keeps `actorId`/`subjectId` - that is the entire point of a user's own "مشارکت‌های من" history, which this same task explicitly asks for. What this task does minimize is the *aggregate/admin* layer built on top of it: `AwarenessDailyAggregate` never stores a raw id, and the admin dashboard route never queries `AwarenessEvent` directly at all. An actual data-retention/purge job for the raw event log (e.g., deleting events older than N days) is a distinct, separately-scoped feature the plan's own wording does not ask this task to build, and none exists yet.
- **`APPLIED` was mapped to "joining a participation role"** (Task 10's existing `joinRole`), the closest existing action in this codebase to "applying to help" - the plan names the event type but does not define which UI action produces it, and no new UI/endpoint was invented to manufacture one. `RESERVED` itself was deliberately left out of `AwarenessDailyAggregate`'s six columns - it is already fully and more accurately derivable from Task 16's own live reservation state (`GET /cards/:id/reservation`), and a raw daily count of `RESERVED` events would double-count a cancel/re-reserve cycle in a way the live state never would.
- **The daily aggregation job aggregates *yesterday*, never *today***, matching Task 13's `space-health` job's own reasoning: at the job's 03:30 run time, today's events are still accumulating, so aggregating it now would produce a permanently-incomplete row for that day; the row is still safely re-computable (idempotent upsert) if the job is ever re-run for the same day.

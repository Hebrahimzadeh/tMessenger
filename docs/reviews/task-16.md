Security:
- **Every mutating action re-derives authorization from the reservation row itself on every call**, never from a client-supplied role/flag: `ownerId`/`reserverId` come from the stored row (ultimately the card's real `authorId`), not from the request.
- **The Idempotency-Key cache is scoped per (`scope`, `actorId`, `key`)**, so one user's retried request can never replay another user's cached result, and a key reused across different actions (`reserve` vs `cancel`) never collides.
- **Only a successful (2xx) result is ever cached.** A request that genuinely failed (wrong state, not the owner, card not found) is never trapped behind a stale cached error - retrying under the same key re-evaluates current reality.
- **The conversation-creation failure path was verified to actually roll back**, not just typed to look like it would - a bad reserver id triggers a real FK violation inside the same transaction as the reservation write, and the test confirms neither row exists afterward.
- No new phone/PII surface: reservations and conversations only ever store user ids and enum/state values; `releaseReason` is free text but bounded (500 chars) and never rendered as HTML anywhere in this task (no UI was added).

Reviewer note:
- **"هر transition ... AwarenessEvent بسازد" is read as "for every transition that has a defined AwarenessEventType," not as license to invent new enum values.** Task 18's own interfaces section fixes the entire awareness vocabulary at `PRODUCED|MEANINGFUL_VIEW|PUBLIC_CONTRIBUTION|RESERVED|PRIVATE_CHAT_STARTED|APPLIED|RESERVATION_CLOSED` - there is no `CANCELLED`/`RELEASED`/`MARKED_IN_USE` value in that list, and Task 16's own plan text never asks for one either. Writing a `CardEvent` for every transition (which this task does, unconditionally) satisfies the domain-audit half of the requirement; inventing awareness-vocabulary values a later task didn't define would very likely need reconciling or removing once Task 18 actually builds its funnel dashboard around the real seven values. The schema, however, adds the full `AwarenessEventType` enum now (rather than a narrower one this task would need to widen later) precisely because Task 18 depends on it existing.
- **`AwarenessEvent`/`CardReservation` model design is deliberately "one row per card, forever," not "one row per reservation attempt."** This directly encodes "reactivation/EXPIRED صفر - fewer states to reconcile, and the terminal check (`isTerminalReservationState`) is the single place that could ever be wrong, rather than being spread across "does another row exist for this card" queries at every call site.
- **The repository's `transition` method is intentionally a dumb CAS primitive with no state-machine knowledge of its own** - `reservation.repository.test.ts`'s last test documents this explicitly: the repository will happily apply any `(expectedVersion, toState)` pair that matches, and it is `reservation.service.ts`'s `assertTransition`/`isTerminalReservationState` that is the one place the actual allowed-transition table is enforced. Keeping that single source of truth in the pure, fully-unit-tested state machine (rather than duplicating transition logic inside a SQL `WHERE state = ...` clause per action) is what let the transition table get its own focused unit tests independent of the database.
- **No app UI or page was added in this task, matching Task 14's own precedent** - the plan's Files list for Task 16 is schema + `card-state-machine.ts` + `reservation.{service,route}.ts` + the messaging port/repository + contracts; no `app/`/`components/` path. Task 17 ("رابط ایجاد کارت و سناریوی نردبان") explicitly owns building `ReservationActions.tsx` and redirecting to `/chats/:conversationId` on a successful reserve - this task's job was to make that redirect target (a real, idempotent `conversationId`) exist and be trustworthy under concurrency, which it now does.
- **`releaseReason` is optional free text, not a fixed enum**, unlike `closeReason` - the plan gives `close` an explicit fixed vocabulary (`RETURNED|COMPLETED|TIME_ENDED|OWNER_CLOSED`) but never enumerates release reasons, so inventing one here would be guessing at categories the plan doesn't specify; a bounded (500-char) free-text field is the more honest choice until a real product need names specific release reasons.

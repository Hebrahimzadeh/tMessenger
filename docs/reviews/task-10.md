Reviewer note:
- **Real, latent migration-ordering bug found and fixed**: Task 09's `mfa` migration folder was named `20260904000000_mfa`, which sorts *before* Task 05's `20260905000000_identity` migration - the one that creates the `users` table `mfa_enrollments` has a foreign key to. This went unnoticed in Task 09 because that migration was hand-applied directly against the already-populated live dev database (see Task 09's own review), never replayed from empty. Running `prisma migrate dev` for this task's own schema change replays *every* migration from a fresh shadow database in timestamp order, which immediately failed with `relation "users" does not exist` - exposing that any genuinely fresh `prisma migrate deploy` (a new environment, CI, or a teammate's first `git clone`) would have failed identically. Fixed by renaming the folder to `20260905000300_mfa` (after its dependencies) and updating the corresponding row in `_prisma_migrations` on the live dev database to match; re-ran `migrate dev` afterward, which completed the full clean replay successfully, and `migrate status` now reports "up to date" across all 6 migrations. This is exactly the kind of defect Task 09's own "run it against a real, fresh-enough scenario, not just the accumulated dev DB" lesson was about - migration order is invisible until something actually replays from zero.
- **Create/update are deliberately split** rather than one endpoint accepting the full definition upfront: `POST /spaces` takes only a `title`, and everything else (purpose, roles, participation methods, ...) is filled in via `PATCH`. This matches "ساخت draft آزاد" (creating a draft should be a low-friction, near-instant action) while still letting `publishSpace`'s minimums apply to the *fuller* definition once the creator has actually filled it in - a single all-at-once creation endpoint would have forced either a much larger required-fields set on day one or a confusing partially-required schema.
- **A deliberate, literal-compliance choice**: unlike `updateSpaceDefinition`'s editor check (creator or space admin, matching the plan's more general "ویرایش ... توسط creator/admin" wording), `archiveSpace` uses the exact same check with **no** implicit SUPERADMIN override, because the plan states this one explicitly as "فقط creator/space-admin مجاز" (*only* creator/space-admin). Adding a staff bypass here would have been scope creep beyond what was asked, not a safety improvement - if a future task needs staff-initiated archival (e.g. for moderation), that should be its own deliberate, reviewed addition.
- **`GET /spaces/:idOrSlug` is the first endpoint in this codebase that behaves differently for an anonymous caller rather than either requiring a session or being unconditionally public** - every prior public endpoint (`GET /users/:username`, `GET /legal/...`) never needed to know *who* was asking. This needed a new primitive (`getOptionalSession`) rather than reusing `requireSession`, which always replies/rejects on a missing session; that would have made a `PUBLISHED` space's page 401 for a logged-out visitor, defeating the entire "دسترسی عمومی فقط PUBLISHED را برگرداند" point of the endpoint existing at all.
- **A second, unrelated environment artifact surfaced while smoke-testing, not a real bug**: an initial live curl call showed `"title":"??? ???? ???????"` and a fallback slug of `"space"` when creating a space with a Persian title passed inline as a `-d` argument - traced to this Windows Git-Bash environment mangling non-ASCII bytes when a shell variable is interpolated directly into a subprocess command line (the exact same class of issue as `PowerShell`'s codepage quirks noted in this project's tooling, just surfacing via `curl`/bash here instead). Confirmed as environment-only, not application-level, by re-running the identical request via `--data-binary @<utf-8 file>` and via a two-line Node `fetch` script, both of which round-tripped the Persian text and slug correctly. Worth remembering for any future manual verification on this machine: never interpolate non-ASCII text directly into a bash/curl command line - write it to a file (or use Node) instead.

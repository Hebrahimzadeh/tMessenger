Reviewer note:
- **Deleting `components/platforms/`'s three named files (plus the equally-dead `PlatformInternal.tsx`) instead of leaving them alongside new real versions was a deliberate call, not an oversight.** `/platforms/:id` has redirected to `/` since Task 12 and nothing in the live app has imported any of these four files since; keeping dead mock components with the exact same names as the plan's real replacements around would only invite a future task to import the wrong one by mistake. `BioModal.tsx`, `MiniAppSheet.tsx`, and `PlatformsList.tsx` were left untouched - they are outside this task's named scope and, while very likely also dead, removing them wasn't asked for here.
- **A genuine, non-hypothetical E2E bug was found and fixed via the real Playwright run, not assumed from reading the code**: the initial `ladder-flow.spec.ts` draft hit three real issues in sequence - a missing login before `/spaces/new` (typeout), Playwright's default substring name-matching colliding "ثبت کارت جدید" with "ثبت کارت" (`exact: true` fixed it), and a strict-mode violation from a transient moment where the comment composer's `<textarea>` still displayed the just-submitted text at the exact instant the new `<p>` also appeared (fixed by scoping the assertion to `p` elements, not the underlying UI, which does clear correctly). None of these were product bugs; all three are now documented, fixed, test-authoring lessons.
- **The "شرح دسترس‌پذیر" (accessible description) the picker collects has no server-side home yet** - `CardAttachment` (Task 14's schema) has no alt-text column, so this field is presentational only within the composer session (used as the `alt`/`aria-label` on the picker's own local preview) and is not sent to, or ever returned by, the API. Persisting it end-to-end would need a small Task-14-schema migration this task's plan does not ask for; flagging this honestly rather than pretending it round-trips.
- **`ReservationActions`'s owner-only `IN_USE` view offers no way back to `RESERVED`** - that transition does not exist in Task 16's own state machine (`IN_USE` only ever closes), so there is nothing for this UI to expose; an owner who marked something in-use by mistake has no undo short of closing it, matching the API's own deliberately narrow transition table exactly.
- **The three feed icons (reaction/reserve/chat) on a real `CardTemplate` card are deep-links into the detail page, never inline stateful actions** - duplicating live reaction/reservation state across both the list and the detail view would risk the two surfaces disagreeing (exactly the class of bug "state button ... نه منطق مستقل client" warns against); keeping exactly one place that ever fetches or mutates that state (the detail page) was judged the safer, simpler design for the MVP, at the cost of an extra click to react from the feed.

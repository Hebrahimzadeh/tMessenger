Security:
- **Real ranking bug found and fixed via an actual live smoke test, not a hypothetical**: see Reviewer note - plain `similarity()`/`%` silently excluded genuine matches once the stored document (title+purpose+audience) was meaningfully longer than the query, which would have made real search results feel broken/empty for exactly the common case of a short 2-3 word query against a fuller space description. Caught because the smoke test used a realistic, non-trivial purpose string rather than a short one matching the query almost verbatim.
- `scope=following` requires a real session both in the route (checked before calling the service) and in the service itself (`FollowingScopeRequiresSessionError` as defense in depth) - a client cannot see another user's follow list by omission.
- Cursors are opaque, versioned-shape base64 blobs (`InvalidCursorError` for anything that fails to decode to the exact expected shape) - a client cannot use a cursor to smuggle an arbitrary SQL-relevant value; every field in it is independently type-checked before being interpolated as a `Prisma.sql` parameter (which itself parameterizes safely, not string-concatenates).

Reviewer note:
- **Real, substantive ranking bug found and fixed, not caught by the initial test suite**: the first repository test written for text search used a query nearly identical in length to the target title, which happened to still clear `pg_trgm`'s default 0.3 similarity threshold. A live smoke test using a *realistic* short query ("باغ محله") against a real space's fuller purpose text ("این بستر برای هماهنگی داوطلبانه‌ی نگهداری باغچه‌ی محله تشکیل شده است.") returned **zero results** for an objectively correct match. Root cause: plain `similarity()` scores two entire strings against each other, so a short query compared against a much longer combined `searchText` dilutes toward zero regardless of whether the query appears verbatim in it (confirmed directly: `similarity(...)` = 0.12, under threshold; `word_similarity('باغ محله', ...)` = 1.0 for the identical pair). Fixed by switching the score expression and filter operator to `word_similarity()`/`<%` (scores the query against its *best-matching substring* of the document - the operation "does this query appear in this document" actually needs), which the same GIN trigram index accelerates equally. Added a repository test reproducing the exact failing scenario (short query, long realistic purpose) so this specific regression can't silently return.
- **A second real bug, this one purely a naming mismatch**: `space-similarity.service.ts`'s `SimilarityResult` originally used `spaceId` while `packages/contracts/src/space-search.ts`'s `spaceSimilarItemSchema` expects `id` - the route's `spaceSimilarResponseSchema.parse({ items })` call then threw on every single request (a genuine `id` field missing), surfacing as an uncaught 500 to any caller. Caught by a route test exercising the real HTTP response shape, not just the pure-function unit tests (which never touched the contract schema at all). Fixed by renaming `SimilarityResult.spaceId` → `id` for consistency with every other space-identifying field in this codebase.
- **Two separately-registered Fastify plugins now share one prefix** (`space.route.ts`'s `spaceRoutes` and this task's `spaceSearchRoutes`, both at `/v1/spaces`) - new to this codebase (every prior module got its own distinct prefix). Verified directly, not just assumed, that Fastify/find-my-way's static-route-wins-over-parametric priority still holds across two separate plugin registrations: `GET /v1/spaces/similar` is not swallowed by Task 10's `GET /v1/spaces/:idOrSlug`, and `GET /v1/spaces` (bare) coexists with Task 10's `POST /v1/spaces` (same path, different method). A dedicated test documents and locks in this behavior so a future refactor that merges or reorders route registration can't silently regress it.
- **"Stable" pagination has an honest, stated limit**: keyset (not offset) pagination guarantees no repeats/omissions caused by the pagination mechanism itself - the property this task's own acceptance line asks for. It does not, and cannot, guarantee a page fetched a few seconds after another one is immune to a *new* space being published or a follower count changing in between; that is normal, expected behavior for any live, mutable dataset under keyset pagination (and considerably better than offset pagination's behavior under the same conditions, which additionally repeats/skips items due to the offset itself drifting). Worth stating explicitly rather than letting "stable" be read as a stronger guarantee than what was actually built.
- **`follow`/`unfollow` do not independently re-check a space's visibility** (unlike `getSpace`'s own creator-or-admin-or-public gate) - a real client's UI would only ever show a follow button on a space it already successfully fetched via `GET`, which already passed that check. Revisited and left this simple deliberately rather than importing `space.service.ts`'s visibility logic into this module for a scenario the plan does not test or ask for; worth reconsidering only if a future task needs `follow` reachable from a context that hasn't already loaded the space.
- **"Health" is honestly a placeholder, not a real health metric**: no engagement/analytics infrastructure exists yet in this codebase (no cards, comments, or participation events until Task 14+), so follower count is used as the one real, already-existing signal - not a claim that follower count is what "health" should mean long-term. This is exactly the kind of rule-based interim measure the plan expects this milestone to use, same spirit as `SpaceCreationGate`'s fixture lists.

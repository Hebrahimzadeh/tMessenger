Reviewer note:
- **Real, significant bug found and fixed via E2E, not any unit test**: `getSpace`'s original design (Task 10) only ever included the `gate` field for the owner/admin view of a *non-published* space - once `PUBLISHED`, the public view is returned unconditionally, `gate` and all, regardless of who is actually asking. Every owner-only UI affordance built on top of that (`SpacePage.tsx`'s `isOwnerView = space.gate !== undefined`, used for both Task 10/12's invite-link generator and this task's own health panel) silently stopped working the instant a space went live - precisely the moment an owner would most want to check its invite link or health. Caught only by extending `spaces.spec.ts`'s real end-to-end flow to visit the just-published space as its own creator and look for the health panel, which genuinely wasn't there. Fixed by adding a real, always-present `canManage: boolean` field to the response (computed identically regardless of publish status) and updating `SpacePage.tsx` to key off that instead of `gate`'s mere presence; `gate` itself keeps its original, narrower meaning (pre-publish moderation state) unchanged. A dedicated regression test (`space.service.test.ts`) explicitly publishes a space and asserts `canManage` stays `true` for its creator afterward, with `gate` correctly still absent.
- **A real architectural decision, not a shortcut**: the actual health computation (`computeHealthStatus`/`computeSuggestions`) and its repository could not reasonably live inside `services/api` alone, because `services/worker` - a genuinely separate deployable process - needs the exact same logic for its daily batch job, and a service reaching into another service's private `src/` tree is not a real dependency a monorepo should have. Rather than duplicate the repository (non-trivial, multi-table Prisma logic that two copies could silently drift apart on) or the pure functions (smaller, but still real business logic, not boilerplate), this task adds `packages/space-health` as a proper third shared package, exactly matching how `packages/database` and `packages/contracts` already work - both `services/api` and `services/worker` depend on it, and it has its own complete, independent test suite (including its own real-Postgres fixtures, built with raw Prisma calls rather than reaching into `services/api`'s Task 10 test helpers, to avoid the reverse dependency problem in the other direction).
- **A real, narrow dependency-version conflict, found and resolved deliberately**: `services/worker`'s own `ioredis` had to be pinned to `^5.11.1`, not the `^6.0.0` `services/api` already uses - `bullmq@5.81.4` bundles/expects ioredis v5's own `Redis` type, and passing a v6 instance failed to typecheck with a genuine structural incompatibility (confirmed directly, not assumed). Each service resolves its own `ioredis` version independently in this npm workspace; `services/api`'s own v6 usage is completely unaffected (re-verified after the change: 464/464 still pass, typecheck still clean).
- **The daily schedule (03:00 server time) is a deliberate, arbitrary-but-reasonable default**, not something the plan specifies a value for - chosen as an off-peak hour, easily changed later via `worker.ts`'s own `pattern` constant without touching any other file.
- **`services/space-health` intentionally leaves `crossRoleCardRate`, `appliedRate`, `reservationClosedRate`, and `reportQuality` at their honest defaults (`0`/`null`)** - each depends on a feature that does not exist yet in this codebase (real cards: Task 14+; reservations: Task 16; reports: Task 27+). The schema and contract carry the full vector the plan names now, so no later task needs a breaking contract change to start populating them for real - but nothing in this task fabricates plausible-looking values for features that aren't built, the same discipline every prior task in this plan has held to.

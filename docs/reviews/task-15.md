Security:
- **Ownership and moderation are re-checked server-side on every write**, never trusted from a prior response: `editComment` checks `authorId` (403 `FORBIDDEN` otherwise, never a 404 that would leak existence-vs-ownership ambiguity inconsistently), `deleteComment` checks author-or-moderator, `pinCard`/`unpinCard` check `isSpaceEditor` fresh each call.
- **No client-controlled HTML ever reaches the DOM.** Comment bodies render as literal React text nodes; the only markup `renderPlainTextWithLinks` ever produces is a same-shape `<a>` for a bare URL match, with a hostile `rel` set on every one of them regardless of the URL's own origin.
- **A soft-deleted comment's text is genuinely gone from every read path** (`CommentView.body` is `null` for a `DELETED` comment both directly from the service and via the route), while the audit trail (`AuditEvent`, `CardCommentRevision` rows) is preserved for moderation/compliance - "حذف متن را پنهان ولی audit را حفظ".
- **Reaction rate limiting is per-user, not global** (`reaction:user:<id>`), so one abusive account cannot exhaust the budget for everyone else; the real deployment uses the same Redis-backed `RateLimiter` already used for OTP requests, not a new mechanism.
- A reply is verified server-side to belong to the same card as the parent (`CrossCardReplyError`) — a client cannot construct a reply that threads across cards even by supplying a valid `parentId` from elsewhere.

Reviewer note:
- **Ranking reorders within a page; it never changes which rows are fetched.** Mixing a score-based ordering with keyset pagination is a real footgun (a naive implementation can skip or repeat rows across pages once ranking depends on data that changes between requests, e.g. a new reaction landing between two page loads). The design here keeps the two concerns fully separate: `card.repository.ts`'s `listCards` still fetches and cursors purely by `(publishedAt, id)`; `card.service.ts` only re-orders the *already-determined* page's rows for display, using the same boundary row (pre-rank) to compute `nextCursor`. This means ranking is deliberately a per-page cosmetic reorder for the MVP, not a global top-K ranked feed — a fine trade-off in the current codebase's scale, and one that never breaks pagination correctness, which a global-ranking approach could not have guaranteed without a much larger change (materialized scores, a stable ranking snapshot, etc.) that this task's plan does not ask for.

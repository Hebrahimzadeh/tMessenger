Reviewer note:
- **Real bug #1, found via E2E, not any unit test**: `proxy.ts`'s public-path allow-list never included `/spaces/`, so every request to `/spaces/[slug]` - including a `PUBLISHED` space's own page, meant to be reachable by anyone - was silently redirected to `/login` before the page ever rendered. Unit/component tests never caught this because they render `SpacePage` directly, bypassing the Next.js middleware entirely; only a real browser navigation through the actual routing stack could. Fixed by adding `/spaces/` to `PUBLIC_PATH_PREFIXES`, mirroring `/u/`'s own precedent (a public prefix whose own `/new`-shaped sibling route still enforces its real gate via `requireUser()`, not the proxy's cheap check) - confirmed via both a unit test (`proxy.test.ts`) and a dedicated E2E test proving `/spaces/new` still redirects an anonymous visitor to login through its own `requireUser()` gate, not the proxy.
- **Real bug #2, also found only via E2E**: a direct browser navigation to a space's own page with a non-ASCII (Persian) slug 404'd with a genuine `SPACE_NOT_FOUND`, even though the space was confirmed `PUBLISHED` in the database and a direct `curl` to the exact same API endpoint succeeded. Traced by logging the actual outgoing API request from a real Playwright browser context: it was double-percent-encoded (`%25D8%25A8...`), meaning `app/spaces/[slug]/page.tsx`'s `params.slug` arrived already percent-encoded for a direct/fresh navigation (rather than auto-decoded, which `<Link>`-driven client-side routing does not exhibit - only a hard page load does), and `SpacePage`'s own `encodeURIComponent()` call encoded it a second time. Fixed by explicitly `decodeURIComponent`-ing `slug` in the page wrapper before passing it down - a safe, idempotent no-op if the value ever does arrive already decoded. No dedicated unit test exists for this specific page wrapper (matching this codebase's existing precedent - `app/u/[username]/page.tsx` and `app/admin/page.tsx` have none of their own either, only E2E coverage); `spaces.spec.ts`'s own full-flow test is what would catch a regression here.
- **A deliberate, bounded scope decision for the space page's nine-section "constant contract"**: header, roles, invite, search, and feed are fully wired against real Task 10/11 endpoints; pins, card-creation ("composer"), tools, and rules/report each show a clear, honest, on-brand "not available yet" message rather than any fabricated content - because no backend exists for any of them until later tasks (pinned/real cards: Task 14+; AI-driven tools: Task 23+; report intake: Task 27+). This is exactly what the plan's own "بخش‌های بدون داده empty-state واقعی داشته باشند" line calls for, not a shortcut - building working versions of features with no backend yet would mean fabricating data this session has been careful never to fabricate anywhere else.
- **The wizard's role suggestions are honestly just starting text, never claimed as AI-derived**: "سازمان‌دهنده" and "همکار" are fixed, generic starting points the user is expected to edit, not an analysis of what they typed in the purpose field - no NLP/AI infrastructure exists anywhere in this codebase yet (Task 24 is where real AI-driven guidance arrives). The plan's own wording ("از متن آزاد ... برای ویرایش دستی بگیرد") is satisfied by giving the user *something* concrete to edit immediately after describing their idea, rather than a blank, more intimidating form - not by pretending to have understood their text.
- **No "creator" name/avatar is shown on the space page** - `creatorId` is a bare UUID in the API response, and there is no user-lookup endpoint this task can call to resolve it to a displayable name (Task 08's public-profile endpoint takes a username, not an id, and no reverse lookup exists). "Creator" attribution is satisfied implicitly, through the owner-view gate (a visitor viewing their own space sees the management affordances; everyone else doesn't) rather than a separately rendered "created by X" line - a real display name would need either a new backend endpoint or Task 10/11's own space contract to embed one, neither of which this task's scope calls for.
- **`/platforms/:id`'s redirect is untestable for an anonymous visitor by construction**: that route was already behind the proxy's login gate before this task (its allow-list never included `/platforms`), so an anonymous request never reaches the page component at all regardless of what it does - `spaces.spec.ts`'s test logs in first, matching the only scenario where the redirect code can actually run (an existing user following an old bookmark).
- **`/spaces/[slug]` is client-fetched, not server-rendered**, the same tradeoff already documented in Task 08's own review for `/profile`/`/u/[username]`-adjacent pages: a Server Component's `fetch()` has no access to the incoming request's cookies, so it could never show the owner/admin view of a not-yet-published space. A `PUBLISHED` space's page is real, correct content either way - it simply isn't rendered server-side for SEO purposes in this task's scope.
